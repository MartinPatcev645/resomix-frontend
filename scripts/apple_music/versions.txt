APPLE MUSIC MATCHER — RESULTS VERSION LOG
=========================================
Each results_*.csv in this folder is one run of the matcher. This file records what the matcher
was doing for that run, so we can explain a score, compare approaches, or roll back to any
version's behaviour. Newest changes are described relative to the version before it.

The comparison workflow: compare_results.py scores a chosen results_*.csv against the client's
manually-verified baseline and records each run as a column in master_results.csv, so all
versions below can be compared side by side.


-----------------------------------------------------------------------------------------------
results.csv   —   VERSION 1  (baseline, "before changes")
-----------------------------------------------------------------------------------------------
Source: converted from results.numbers via numbers_to_results_csv.py (this was our very first run,
        kept in Apple Numbers). 225 tracks; 187 got an apple_song_id, 38 NOT_FOUND.

Behaviour:
  - Apple search LIMIT = 1. We took Apple's #1 result and trusted it — no candidate scoring.
  - QUERY was built from the DB metadata (ID3): "artist - title" (artist + title from the
    database), sent as the search term.
  - MATCH DECISION was duration-only: compare our DB duration against the chosen track's Apple
    duration; if they matched (within tolerance) we set is_match = True, otherwise False
    (N/A when we couldn't judge / nothing was found).

Known weakness this exposed:
  - Trusting result #1 means when Apple returns a (Dub)/(Mixed)/(Radio) cut first, we accept the
    wrong version even though the correct track sits at position 2-5.
  - No fuzzy title/artist check, so a plausible-but-wrong #1 could still pass on duration alone.


-----------------------------------------------------------------------------------------------
results_1.csv   —   VERSION 2  (top-5 + fuzzy + numbers + strict duration; DB metadata AS-IS)
-----------------------------------------------------------------------------------------------
NOTE: the first results_1.csv (an early top-5 run) was deleted and re-generated with the
refinements below, so this section describes the CURRENT matcher.

What it does now (and what changed vs Version 1):

  1. TOP-5 CANDIDATES (SEARCH_LIMIT = 5), not just #1. We fetch the top 5 songs and pick the
     best ourselves, so the correct track at position 2-5 can still win over a wrong #1.

  2. FUZZY MATCHING (rapidfuzz) on "artist title" (compared lowercased & unicode-cleaned, with
     generic (Original/Extended Mix) removed from BOTH sides for the comparison only):
       - token_set_ratio  -> "is this the right base song?" (ignores extra tokens like "(Dub)",
         so a Dub and the exact track both score ~100). This is the qualifying score.
       - token_sort_ratio -> penalises extra tokens; used only as the final tiebreaker.
     A candidate must reach FUZZY_THRESHOLD = 85 on token_set_ratio to be eligible.

  3. TITLE/ARTIST USED AS-IS FROM THE DATABASE — NO cleanup. (Changed.) We no longer strip
     leading track numbers, [labels], "(N)" disambiguators, etc. The earlier cleanup was
     corrupting real titles (e.g. "2 + 2 = 5" -> "+ 2 = 5", "123 BPM" -> "BPM", "2Ms" -> "Ms",
     "4 The Luv Of Music" -> "The Luv Of Music"). The search query is the DB "artists - title"
     verbatim, with the ONE exception that generic "(Original Mix)" / "(Extended Mix)" is removed
     from the search term (Apple lists the plain title) — and also from the fuzzy comparison.

  3b. UNKNOWN-ARTIST FALLBACK. (New.) Some DB rows have artist = "Unknown" and the title set to
      the raw filename. ONLY in that case we extract artist + title from the filename
      ("Artist - Title.ext", split on the first " - "). A leading track number is removed ONLY if
      it is "N. " (number, dot, space) or "N - " (number, spaced dash); a number that is part of
      the artist ("20 Dub Person", "01 -Artist") is left intact. Rows that already have a real
      artist are untouched (still fully as-is).

  4. NUMBER GATE. (New.) Integer tokens in the title must match between our title and the Apple
     candidate. A number mismatch = a different track, so it fails the match even at fuzzy 100.
     This kills false positives like "123 BPM" wrongly matching "115 Bpm". (Numbers in ARTIST
     names, e.g. "84Bit", "Kx5", are ignored — only title numbers are compared.)

  4b. WHITESPACE-INSENSITIVE FUZZY. (New.) Alongside token_set_ratio we also compute a
      spaces-removed ratio and keep the HIGHER of the two, so spacing/punctuation quirks like
      "2 + 2 = 5" vs "2+2=5" don't tank an otherwise-exact match. Taking the max only ever raises
      a score, so nothing that matched before can regress.

  5. DURATION RULE — STRICT (DURATION_TOLERANCE_MS = 10000, i.e. +/- 10s). (Reaffirmed.)
     Same title but a different duration usually means a DIFFERENT track, and we always want the
     proper track, so we reject on any duration difference beyond 10s. The ONLY exception: if OUR
     title explicitly says Extended Mix / Extended Remix / Radio Edit, the Apple cut may be shorter
     (apple <= ours + 10s), because that's the same song's shorter edit. Detected from the title.

  6. PRIORITY / SELECTION among the top-5:
       (a) numbers match  ->  (b) token_set_ratio (highest)  ->  (c) smallest duration difference
       ->  (d) token_sort_ratio (tiebreak).
     A candidate "qualifies" (is_match = True) only if fuzzy >= 85 AND numbers match AND the
     duration gate passes. Otherwise the best candidate is still surfaced with is_match = False so
     the row (and its song_id) stays reviewable. is_match = N/A only if our duration is missing.

  7. UNICODE hardening (low priority). (New.) NFC-compose so "E + accent" becomes a single "É"
     (more likely to match Apple), and drop invisible/zero-width format characters.

  8. OUTPUT columns vs Version 1: adds apple_match_score (winning token_set_ratio) and
     apple_chosen_rank (which of the top-5 we picked).

  9. CONSOLE now prints, per track: the query + our duration, then one line for EACH of the 5
     Apple candidates (artist - title (duration) | fuzzy | dur:OK/NO | num:OK/NO), then a final
     verdict line (which candidate matched / no match / nothing found). The chosen row is marked "*".

HOW TO ADD THE NEXT VERSION
-----------------------------------------------------------------------------------------------
Running apple_music_test.py auto-versions the output (results.csv -> results_1.csv -> results_2.csv ...).
When you make a matcher change and produce a new results_N.csv, append a section here describing
what changed vs the previous version and why, then re-run compare_results.py pointing at the new
file to add its column to master_results.csv.
