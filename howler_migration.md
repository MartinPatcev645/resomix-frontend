Migrating to Howler.js and Peaks.js for Audio Playback and Waveforms
Current Dual-Player Architecture and Challenges
Your existing setup uses a dual-player architecture: WaveSurfer.js (v7.x) is handling waveform display with precomputed peak data, while an HTML5 <audio> element (managed via custom hooks/stores) handles actual playback[1]. This was implemented to overcome earlier issues (e.g. iOS audio context limits by sharing one AudioContext, and using WaveSurfer’s MediaElement backend)[2]. In practice, this means WaveSurfer draws the waveform and tracks progress, but you manually sync it with the audio element through a central store.
However, this approach has introduced several issues[3]:
•	Seek/Buffering Delays: On slow networks, seeking can cause noticeable buffering delays or “stuttering” in playback[4]. The current audio loading is not fully utilizing range requests for smooth seeking.
•	Waveform Sync Glitches: During scrubbing (e.g. dragging the waveform on iOS), WaveSurfer sometimes misbehaves – some iOS devices jump to the next track instead of seeking properly[5].
•	Complex State Management: Keeping WaveSurfer’s progress in sync with the audio element via the store adds complexity and occasional sync issues.
•	iOS Limitations: Although you’ve integrated the MediaSession API for lock-screen controls and used silent-audio hacks to unlock playback on iOS, there are still issues like the player disappearing after interruptions (calls/alarms)[6]. Resuming playback after an interruption requires user intervention, indicating the current solution isn’t fully robust.
Why Howler.js + Peaks.js? Migrating to Howler.js for audio and Peaks.js for waveform visualization aims to simplify this architecture and resolve the above issues. Howler will replace the custom audio element logic with a battle-tested, cross-browser audio engine, while Peaks.js will render the waveform from your precomputed data without interfering with playback. This separation of concerns (audio vs waveform) should yield a more stable and maintainable player.
Benefits of Howler.js for Audio Playback
Howler.js is a widely used JS audio library known for its simplicity and reliability across platforms[7]. Adopting Howler offers several immediate benefits:
•	Streamed Loading for Large Files: Howler can stream audio efficiently using HTML5 Audio under the hood, so the user doesn’t have to download the entire MP3 before playback begins. This is crucial for 5–10 MB tracks on slow networks. By enabling HTML5 mode, Howler will use the browser’s native streaming/buffering (with range requests), drastically reducing initial load times and memory usage[8]. Playback can start as soon as the first chunk is buffered, and seeking will trigger fetching only the needed ranges, leveraging the server’s range support.
•	Simpler, Consistent API: Howler abstracts away many browser quirks (media formats, Web Audio vs HTML5, etc.) behind a clean API[7]. This means far less custom event wiring and manual state syncing in your React app. You can play, pause, seek, or change volume with straightforward method calls, and listen to events like onplay, onpause, onend, etc., instead of multiple DOM event listeners.
•	Cross-Platform Audio Fixes: Howler is battle-tested on mobile browsers. It handles Web Audio API unlocking on iOS and falls back to HTML5 audio when needed[9][10]. It also abstracts browser inconsistencies (e.g. differences in how Safari handles audio) to provide a uniform experience[7]. In short, many of the hacks you implemented (shared AudioContext, iOS flags) can likely be removed in favor of Howler’s internal handling.
•	Performance and Stability: By managing its own audio pool and automatically caching sounds, Howler ensures efficient resource use[11]. It will free you from low-level buffer management, and proper cleanup of audio objects is handled for you. The result is a more stable playback over time with fewer memory leaks or context issues[12].
In summary, Howler will simplify your code and improve playback reliability: “Faster playback initiation, responsive controls, and robust resource management ensure a better user experience”[13]. Many large web apps use Howler, so it’s a proven solution.
Using Howler.js in React for Streaming Audio
Installing and Setup: Install Howler (latest 2.x, e.g. v2.2.3) via npm. Then, in your React player code, you can import and use the Howl class to create sound instances. For example:
import { Howl, Howler } from 'howler';

const sound = new Howl({
  src: [audioUrl],  // MP3 source URL for the track
  format: ['mp3'],  // since your files are always mp3
  html5: true,      // use HTML5 Audio for streaming
  preload: true,    // auto-load the file (default true)
  volume: initialVolume,
  onplay: () => { ... },   // hooks to update state/store
  onpause: () => { ... },
  onend: () => { ... },
  onseek: () => { ... }
});
Key options:
•	html5: true – This forces use of the HTML5 Audio element instead of Web Audio API. For large files, this is recommended so that playback can start immediately and stream in the background (no full download needed)[14][15]. It also tends to be more iOS-friendly for continuous playback. With html5:true, Howler will create an internal <audio> element and load the source in streaming mode (honoring your server’s Accept-Ranges support).
•	preload: true – By default Howler preloads when you instantiate the Howl. You can leave this true for the current track so it begins buffering as soon as the user triggers play. (If you only want to create the Howl without downloading until later, you could set preload:false and call sound.load() manually when ready.)
•	format – Specifying ["mp3"] can help avoid any format auto-detection issues. Not strictly required if extension is .mp3, but explicit is safe.
•	Event Callbacks – Use these to sync with your React state/store. For example, onplay can dispatch an action to set a global isPlaying flag, onend can trigger your playNext() logic (autoplay next track), etc. Howler’s events make it easy to integrate with your existing usePlayerStore and usePlayerManager logic (e.g. call playNext() inside onend).
Playback Control: With Howler integrated, you will manage playback via the Howl instance methods instead of the <audio> DOM APIs. Important methods include sound.play(), sound.pause(), sound.stop(), and sound.seek(seconds) for jumping to a position. You can retrieve the current time with sound.seek(). Volume and other properties (looping, playback rate) can also be controlled through Howler’s API. This greatly simplifies your code since you no longer need to manually sync an <audio> element’s properties with the store – you can query or update the Howl directly.
Smooth Seeking with Range Requests: When a user seeks to a new position, Howler (in HTML5 mode) will rely on the browser’s audio element to handle it. The browser will automatically issue a range HTTP request for the new position of the MP3, thanks to your server’s range support. To optimize this:
•	If the user seeks within the already buffered range, playback will be instant (no new network request, it’s already in the buffer cache).
•	If the user jumps beyond buffered data, the audio element will internally fetch that byte range. You don’t need a special handler for this – simply calling sound.seek(newTime) will pause the current playback and request the needed data; playback will resume as soon as the data arrives.
•	Optional: To be extra safe, you can call sound.pause() (or sound.stop()) just before a large jump to abort the previous buffering. In practice, setting a new seek() on the Howl should handle this (the old request is abandoned by the media element once a new seek is initiated). The browser will also cache previously downloaded ranges, so seeking back to a point you already buffered should be instant.
Buffering Feedback: You might want to listen to the audio element’s onprogress or buffer events to show buffering progress. Howler doesn’t expose a direct buffering event, but since you have access to the Howl’s HTML5 audio node (more on this below), you can check audioNode.buffered to see buffered time ranges. This can help display a buffer bar if desired.
Preloading the Next Track: A great advantage of Howler is that you can easily load the next track in advance (if the user enabled autoplay). There are two strategies:
1.	Instantiate Next Howl Early: When track A starts (or after a certain time), create the Howl for track B with preload:false. Once track A is near the end or fully buffered, you can call nextHowl.load() to start loading B in the background. Since the peaks JSON for track B is small (~2–3 KB), you can also fetch that at this time. By the time track A finishes, track B will be partially or fully buffered, making the transition seamless.
2.	Post-Track Preload: Alternatively, upon onend of track A, immediately play track B via Howler. Howler will start B’s playback (if autoplay) and buffer on the fly. To also warm up track C, you could instantiate track C’s Howl at this point. This is slightly less aggressive but still reduces wait before track C.
Given your description, the first approach is closer to what you want: “once track A is fully loaded, fetch peaks and audio for track B”. You can detect when A is fully loaded by checking sound.state() (Howler returns "loaded" when done) or monitoring the buffered range reaching the duration. Once that happens, call new Howl({src: B, html5:true, preload:true, ...}) for track B in the background. You don’t even need to play it; just creating it with preload will start buffering B immediately. Then, when you actually call soundB.play(), it will start instantly.
Memory & Cleanup: Each Howl should be unloaded when you no longer need it. Howler will keep decoded audio in memory for Web Audio mode, but in HTML5 mode the browser manages buffering. Still, it’s good practice to call sound.unload() on a Howl you’re done with (e.g., when skipping a track before it ended) – this will destroy the internal audio element and free resources. If you reuse a single Howl by changing source (not typical), ensure you properly handle old data. However, the simpler approach is to use one Howl per track and let it go out of scope or unload it when transitioning to the next track.
Integrating Peaks.js for Waveform Visualization
Peaks.js is an open-source waveform viewer from the BBC, designed to display and interact with audio waveforms using precomputed data[16][17]. It is well-suited to your use case: you already generate a JSON array of normalized peaks (one value per second of audio) on the server, which is exactly the kind of precomputed waveform data Peaks.js can use. Using Peaks.js will allow you to drop WaveSurfer entirely for rendering the waveform.
Installation: Peaks.js is available on npm. Note that it has peer dependencies on konva (for canvas drawing) and waveform-data (for parsing waveform files)[18]. Install all three:
npm install peaks.js konva waveform-data
It’s advisable to use a specific Konva version if needed (the Peaks docs mention using Konva 8.x for compatibility[19]).
Providing Waveform Data: Since your backend provides JSON peaks via /peaks?uuid=trackId, we want to feed that into Peaks.js. Peaks supports two ways to get waveform data[20]:
•	Precomputed Data: Supply a URL to the JSON (or binary .dat) file via the dataUri option. Peaks will fetch and parse it for you[21].
•	Web Audio Analysis: Provide an AudioContext and Peaks can analyze the audio file in the browser to derive peaks (not recommended for long files, as it requires downloading the whole file and heavy CPU)[22].
We will use the precomputed JSON approach, which is ideal for longer tracks[23]. Your existing JSON (2–3KB for ~3 minutes) is small and quick to load, allowing the waveform to render almost instantly, independent of the audio file download. This matches how BBC’s audiowaveform tool is intended to be used: compute wave data server-side and send it to the client for fast rendering[24].
Note: Peaks.js expects the JSON in the format produced by audiowaveform (the BBC tool)[25]. That format typically includes metadata (sample_rate, bits, length) and a flat array of values where each pair of numbers represents a min and max amplitude for a segment of audio. For example, [ -30, 26, -29, 30, ... ] would mean a segment with a minimum of -30 (valley) and maximum of 26 (peak)[26]. In your case, it sounds like your JSON is a list of normalized positive values (0.000–1.000) at 1-second intervals (essentially the peak of each second). If so, you might need to adapt it slightly for Peaks.js: - Easiest approach: have Peaks treat your values as the “max” values and simply mirror them for the negative side. Because most waveforms are roughly symmetrical, using the same magnitude for the negative half is visually acceptable[27]. For example, if one second’s peak is 0.65, you could represent it in data as [-0.65, 0.65]. - Alternatively, modify your server to output an audiowaveform-style JSON (8-bit data). This might involve scaling your 0–1 values to an 8-bit range and interleaving negative values (perhaps just negating each to get a symmetric pair). The Quadio team followed a similar approach: they filtered out negative values from audiowaveform data and normalized positives to a percentage scale[28][29], effectively storing only peaks. For visualization, they then mirrored those peaks to draw a full waveform since it “is both acceptable visually and efficient memory-wise”[27].
If your waveforms looked correct in WaveSurfer with the single array of peaks, likely WaveSurfer was auto-mirroring them. Peaks.js may require the explicit min/max. You can experiment by feeding your JSON directly – if the waveform appears only on one side or very flat, you’ll need to adjust to provide negative values as well.
Initializing Peaks.js: In your React waveform component (e.g. inside a useWaveform hook or WaveformPlayer component), you will initialize a Peaks instance once the audio and peaks data are ready. For example:
import Peaks from 'peaks.js';

useEffect(() => {
  if (!audioRef.current || !peaksData) return;
  const options = {
    containers: {
      // Use a single container for the waveform
      overview: waveformContainerRef.current 
    },
    mediaElement: audioRef.current,
    dataUri: {
      json: `/peaks?uuid=${trackId}`  // or use a pre-fetched data object
    },
    height: 80,          // e.g., 80px height for the waveform
    zoomLevels: [256, 512, 1024],  // optional zoom levels (not crucial if no zoom UI)
    // You can also set other options like zoomView if needed, or waveform color via CSS.
  };
  Peaks.init(options, (err, peaks) => {
    if (err) {
      console.error("Peaks init failed:", err);
      return;
    }
    peaksInstanceRef.current = peaks;
    // You can now use peaks instance (e.g., peaks.points, segments, etc. if needed)
  });

  // Cleanup on unmount or track change:
  return () => {
    peaksInstanceRef.current?.destroy();
  };
}, [audioRef, peaksData, trackId]);
Important notes for this setup:
•	Container: You can use a single container div for the waveform. Peaks.js supports a dual-view (zoom view and overview) if you provide both, but since you want a static full-width waveform (like SoundCloud), a single overview is enough. Setting containers.overview to your div and omitting the zoomview will give one static waveform that fills the container width.
•	Media Element: Here, audioRef.current should be the actual HTMLAudioElement. If you use Howler with html5:true, it creates an internal audio element. You have two ways to supply it:
•	Use the Howler’s audio node: Although not officially documented, Howler exposes the underlying audio element in its internal data. For example, sound._sounds[0]._node references the HTML5 Audio element for that Howl (assuming one sound instance). You can obtain this after you create the Howl (and perhaps after calling sound.load() or sound.play() to ensure it’s initialized). Passing that node to Peaks will let Peaks listen to its timeupdate events and control playback position. This approach effectively ties Peaks’s timeline to Howler’s audio.
•	Use a dedicated audio element in the DOM: Alternatively, you could maintain a hidden <audio> element and point Peaks to it, and not use Howler’s HTML5 mode. However, that would defeat the purpose of using Howler for playback. The first approach (accessing Howler’s audio element) is preferable so you have a single source of truth for audio. Just keep in mind that _sounds[0]._node is an internal property; in practice Howler’s internal API is stable, but use it carefully.
If using the Howler node, ensure you initialize Peaks after the Howl is created and its audio node exists. You might call Peaks.init inside Howler’s onload or onplay callback to be safe, or simply a short delay. Once attached, Peaks will sync to that element’s playback.
•	Data URI vs Data Object: For convenience, using dataUri.json with your API endpoint is fine – Peaks will fetch the JSON itself. This keeps your React code simple (no need to fetch peaks JSON separately). If your API requires auth headers or you already have the data, you could also fetch it in React and then use the waveform-data library to create a WaveformData object to pass to Peaks. But in most cases, providing the URL is easiest[21].
•	Rendering and Appearance: Peaks.js will draw the waveform on a Canvas (via Konva). By default it uses a blue waveform on a grey background (if I recall correctly). You can customize colors and styles via CSS or options. For example, adding CSS to target the canvas or using Peaks options for waveform color (the documentation mentions a waveformColor property). If needed, you can find those in the Peaks API docs. Also, your container’s dimensions determine the waveform’s size – you can set the container width to 100% (fluid) and a fixed height (e.g. 80px) via CSS or via the height option as shown.
•	Interactivity: Peaks waveforms are interactive – users can click or drag to seek if the media element is attached. By default, Peaks will allow scrolling/zooming if you enabled a zoomview, but with one static view, clicking on the waveform might not automatically seek the audio. You have a couple of options to implement seeking:
•	Use Peaks’ events: Peaks emits events like player_seek or player_time_update when the media element seeks or time updates[30]. If Peaks doesn’t automatically handle click-to-seek, you could listen for a click on the canvas. Peaks doesn’t provide a high-level “on waveform click” callback out of the box, but you can add a listener to the container element. Calculate the clicked time as (clickX / containerWidth) * audioElement.duration. Then call howl.seek(time) to jump the playback. Because Peaks is connected to the same audio element (via Howler), it will update the playhead position accordingly.
•	Use Peaks’ internal player: If you prefer, Peaks’s instance has a peaks.player object that proxies the media element. For example, peaks.player.seek(time) or peaks.player.play() will control the audio element. Since Howler is also controlling the same element, it’s usually better to stick to one controller (Howler) to avoid confusion. But simple actions like peaks.player.seek() should effectively do the same as howl.seek(). Just be cautious about conflicts. In practice, clicking the waveform and calling howl.seek() is straightforward.
With the waveform tied to the actual audio element’s time, Peaks will automatically update the progress indicator as the track plays. You no longer need to manually set progress in the store for the waveform – Peaks listens to the media element’s timeupdate events (fires ~4/sec) and will move its playhead cursor accordingly. This should eliminate the sync issues you faced and offload that work to the library.
Finally, clean up the Peaks instance when a track is unloaded or the component unmounts. As shown, peaksInstance.destroy() will remove event listeners and canvases[30]. You’ll likely re-initialize Peaks for each new track (since each track has its own peaks data and audio element).
Ensuring Smooth Playback on All Devices (iOS, Android, Desktop)
Using Howler with HTML5 audio and Peaks should maintain (or improve) compatibility with mobile devices:
•	iOS Playback & MediaSession: Since Howler’s HTML5 mode uses a real audio element, it will behave similarly to your current <audio> setup. You can continue to use the Media Session API for metadata and action handlers. For example, after calling sound.play(), set navigator.mediaSession.metadata with the track info (title, artist, artwork) as you did before. This will update the lock screen info. The play/pause, next/prev action handlers can be set the same way – those will call your Howler controls. There is no conflict here; Howler does not manage MediaSession internally, so your existing integration can remain.
In practice, iOS should treat Howler’s audio just like any audio element. The lock screen controls will show up when audio is playing. One difference: if you previously relied on an <audio> element’s attributes (like controls, playsinline, etc.), note that Howler’s created audio element is not in the DOM, but it should implicitly behave as if playsinline (because it’s audio, not video). iPhones historically required playsinline for videos to avoid fullscreen; audio does not require that. So you likely won’t need to manually set that. If you find any quirk (e.g., audio not resuming after interruption), you might consider accessing the audio node and setting audioNode.setAttribute('autoplay','') or others, but this typically isn’t needed when the user initiated playback.
•	Automatic Resume After Interruptions: As noted, one issue was that after a phone call or alarm, the audio did not resume on its own[6]. This is a common Safari behavior – it pauses the audio and doesn’t auto-restart it. Howler by itself won’t override that (browsers usually prevent auto-resume for user safety). One approach is to listen for the visibilitychange or the audio’s pause event and detect if it was paused while it should be playing (indicating an external interruption). You could then attempt to resume when the page becomes visible or the interruption ends. However, Safari might block that because it’s not a direct user action. At least, with Howler, you can reliably catch the pause event via onpause callback. Logging or handling that (maybe by displaying a “Tap to continue” prompt) could improve UX slightly.
Overall, this remains an iOS limitation not fully solvable via code – but using Howler doesn’t worsen it. The continuous playback from track to track (autoplay next) should work as long as the initial play was user-initiated. Reusing a single audio element (which Howler does by keeping it alive while the Howl exists) means autoplay next should not be blocked by iOS. Many Howler users have implemented playlist autoplay successfully on iOS, so you should be fine.
•	Audio Tag Attributes: In your current AudioProvider, you likely set attributes like muted={true} (for the silent unlock hack), playsInline, etc. With Howler, much of that hackiness can be removed. You no longer need a dummy silent audio to unlock Web Audio – because we’re using HTML5 audio, the user’s first tap on play is enough to satisfy iOS’s gesture requirement. Howler also internally calls a method to unlock audio on iOS if using WebAudio, but in our case we stick to HTML5. So the startup flow is simpler. You won’t need to manually manage multiple AudioContexts or keep a dummy audio element around. This reduces overhead and avoids hitting the iOS 6-audio-context limit entirely.
•	Stability & Testing: Since Howler and Peaks are new in your stack, be sure to test on various devices:
•	Desktop: All modern browsers (Chrome, Firefox, Safari, Edge) should work with Howler. Howler falls back to WebAudio or HTML5 as needed. Peaks.js uses Canvas, which is well-supported (even IE11 with polyfills if needed, but likely not a concern).
•	Mobile Android: Chrome/Firefox on Android should behave well. HTML5 audio streaming is standard.
•	Mobile iOS (Safari, Chrome): These browsers share WebKit under the hood, so performance will be similar. Test seeking and track transitions on a real device. Ensure that the MediaSession controls (skip, pause from lock screen) trigger the expected Howler events. You might need to handle the navigator.mediaSession.setActionHandler('pause', ...) by calling sound.pause() for example.
If any iOS quirk appears (e.g., a need to call Howler.mobileAutoEnable = true – which is actually true by default – or adjusting volume differences), consult Howler’s documentation or known issues. Howler’s GitHub issues can be a good resource if something like “iOS 15 audio not playing until interaction” comes up, but since we require a user tap to play anyway, we should be within the rules.
Best Practices from the Community (Howler + Peaks in React)
Looking at similar integrations on forums and StackOverflow, a few tips emerge:
•	Maintain Modular Components: Keep your React components for playback and waveform separate, but allow communication via props or a shared store. For example, your InputPlayer (persistent player) can manage the Howler instance and pass down current time or duration to a Waveform child if needed. However, with Peaks handling its own state, you might not need to constantly pass down “currentTime” – Peaks will derive it from the audio.
•	Handle Lifecycle Cleanly: When switching tracks, destroy or reuse resources appropriately. You might destroy and re-init Peaks for the new track’s data. For Howler, you’ll likely stop/unload the old Howl and create a new one for the new track (unless you reuse one Howl and just call sound.stop() then sound.src = newUrl via Howler’s API – but Howler doesn’t have a simple method to change source on an existing Howl, so new instance per track is fine).
•	Version Choices: Use the latest stable Howler 2.x (which as of now is 2.2.x) – it includes many fixes for mobile. For Peaks.js, use the latest 1.x release (Peaks 1.4.x). There is a 3.0 beta, but it’s safer to stick with stable. Ensure Konva (the drawing library) is a compatible version (e.g., Konva 8.4 as recommended)[31].
•	Peaks Data Resolution: You mentioned one peak per second. That yields ~180 points for a 3-minute track, which gives a decent coarse waveform. If you wanted a more detailed waveform (smoother shape), you could increase the sampling (e.g., 2–4 peaks per second). However, that will increase the JSON size proportionally. Many implementations (like SoundCloud or Quadio) use around 100–300 points for the entire track[32] – so your 180 points is in line. It’s a trade-off between detail and data size, but since 2–3KB is trivial, you have room to increase resolution if the bars look too blocky on wide screens. For now, staying with your current approach is fine and “the waveforms look fine in that configuration” as you noted.
•	Remove WaveSurfer Completely: Once Peaks and Howler are in place, you can drop WaveSurfer.js (and its React wrappers) from your project. This eliminates that potential source of interference. It also means you can remove the shared AudioContext hack you had for WaveSurfer (no more 6 context limit issues)[2]. The code will be lighter and likely use less CPU, since Peaks.js drawing is relatively efficient and happens once (no continuous canvas re-draw except the small playhead moving).
In summary, the migration path is:
1.	Integrate Howler in your usePlayerManager or a similar central place: instantiate a Howl for the current track, manage play/pause/seek through it, and tie its events to your store (for UI state like play/pause buttons, track progress, etc.).
2.	Integrate Peaks.js in your waveform component: provide it the peaks JSON URL and the audio element (from Howler) to sync with. Use its rendering for the waveform display and attach an event for seeking on user click.
3.	Remove/replace old logic: Strip out WaveSurfer usage (useWaveform hook, WaveformPlayer component logic) and any manual audio element event handling that overlaps with Howler. For example, if you had audio.onended = playNext, you’ll use Howler’s onend instead. If you had timers or requestAnimationFrame updating progress, you can remove those and rely on Peaks or Howler’s events.
4.	Test thoroughly across different scenarios (autoplay on/off, manual seeking, switching tracks quickly, network throttling, mobile background/foreground) and adjust as needed.
By following this plan, you’ll leverage Peaks.js for instant waveform display from your precomputed data (ensuring even a 10-minute track’s waveform loads in a snap), and Howler.js for rock-solid audio playback (smooth streaming and simplified control). This modular approach (Howler for audio, Peaks for waveform) is commonly recommended – one Stack Overflow answer even suggests “integrate specialized waveform libraries alongside Howler.js, maintaining a modular and efficient architecture”[33]. You’ll end up with a more maintainable codebase and a better user experience: snappier load times, reliable seeking, and consistent behavior across all browsers and devices[8][7].
