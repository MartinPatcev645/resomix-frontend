4. Infrastructure Resilience and High Availability
Rights holders are deeply concerned with service reliability. A "dual-server" setup, while cost-effective, represents a Single Point of Failure (SPoF). If the Alwyzon server hosting the API crashes, the service goes dark. If the Hetzner storage server fails, the music library becomes inaccessible. To pitch to enterprise partners, Resomix must demonstrate a High Availability (HA) architecture.

4.1 Network Redundancy with Floating IPs and Load Balancing
Hetzner Cloud supports "Floating IPs"—public IP addresses that can be dynamically reassigned between servers. This feature is the cornerstone of a cost-effective HA setup. The recommendation is to deploy a pair of load balancers (running HAProxy) fronted by a Floating IP. A daemon like keepalived runs on both load balancers, exchanging "heartbeat" signals (VRRP protocol). If the primary load balancer fails, keepalived on the secondary unit detects the silence and instantly claims the Floating IP via the Hetzner API. This failover happens in seconds, often transparently to the user.
This setup ensures that the entry point to the application is resilient. Traffic is then distributed by HAProxy to the backend API nodes. This allows for "zero-downtime deployments," where one API server can be updated while the other handles traffic, satisfying the requirement for continuous service availability.

4.2 Database Clustering and Failover
The database is the source of truth for metadata, user rights, and similarity vectors. Losing access to it is catastrophic. The current setup likely uses a single database instance. There are two primary paths to HA for the database layer:

4.2.1 Synchronous Replication: Galera Cluster
For maximum data safety, a MariaDB Galera Cluster is the gold standard. It uses synchronous replication, meaning a transaction is not confirmed until it is committed to all nodes in the cluster. This guarantees zero data loss (RPO=0) if a node fails. However, Galera requires a minimum of three nodes to establish a quorum and avoid "split-brain" scenarios (where two parts of a cluster think they are the primary). This increases infrastructure costs but provides the strongest consistency guarantees.

4.2.2 Asynchronous Replication with Orchestrator
Alternatively, a Master-Slave topology managed by orchestrator is often more performant for read-heavy workloads like music search. In this setup, one Master handles writes, while multiple Slaves handle reads. orchestrator monitors the topology; if the Master dies, it automatically promotes the most up-to-date Slave to be the new Master and reconfigures the others to follow it. This setup is faster for writes but carries a tiny risk of data loss (sub-second) during failover. Given the read-heavy nature of a music discovery service, this may be the optimal trade-off between performance and resilience.

4.3 Private Networking and Isolation
Security questionnaires from labels will ask about network isolation. Database servers and internal APIs should never be exposed to the public internet. Hetzner’s vSwitch (Cloud Networks) functionality allows the creation of a private Layer 3 network (e.g., 10.0.0.0/16). All backend communication—between the API and the DB, or the API and the Storage—must occur over this private network.
Firewall rules (using iptables or Hetzner’s Cloud Firewall) should be configured to strictly implement a "default deny" policy. The database port (3306) should only accept connections from the private IP addresses of the API servers. This isolation mitigates the risk of external attacks targeting the data layer.
