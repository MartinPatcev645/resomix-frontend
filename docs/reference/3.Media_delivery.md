3. Secure Media Delivery: HLS and Stream Protection
The current "basic security" setup likely implies standard file serving or simple token authentication. This is insufficient for licensed music. Major labels require that content be protected from "stream ripping"—the automated downloading of audio streams for permanent offline storage. To meet this requirement, Resomix must transition from progressive download (MP3/WAV) to encrypted HTTP Live Streaming (HLS).

3.1 HTTP Live Streaming (HLS) Architecture
HLS works by segmenting an audio file into a sequence of small chunks, typically .ts (MPEG-2 Transport Stream) or fragmented .mp4 files, each lasting 6 to 10 seconds. These segments are indexed in a manifest file (.m3u8). This architecture allows for Adaptive Bitrate Streaming (ABR), where multiple versions of the same track are encoded at different bitrates (e.g., 128kbps, 320kbps). The player client automatically switches between streams based on the user's network conditions, ensuring uninterrupted playback—a critical user experience factor for mobile usage.

3.2 Encryption Standards: AES-128
To prevent users from simply downloading the .ts segments and reassembling the file, the industry standard mandates AES-128 encryption. In this scheme, every segment is encrypted with a 128-bit key. The manifest file contains a specific tag, #EXT-X-KEY, which points to the URL where the player can retrieve the decryption key.
For a robust implementation, Resomix should utilize the "envelope encryption" method supported by FFmpeg. During the transcoding process (converting raw FLACs to HLS), FFmpeg generates the encrypted segments and the key. Crucially, the key itself must never be stored publicly. It should be served via an authenticated API endpoint that validates the user's active session and subscription status before returning the key binary. This ensures that even if a user obtains the .ts files, they are useless without the key, which can only be retrieved by a valid, logged-in user.

3.3 Tokenized Access Control and Link Expiration
Protecting the encryption key is half the battle; protecting the delivery bandwidth and access to the manifest is the other. This is achieved through signed URLs or signed cookies, implemented via the Nginx secure_link module or Cloudflare’s Token Authentication.

3.3.1 Nginx secure_link Implementation
In the proposed Alwyzon/Hetzner architecture, Nginx acts as the reverse proxy and media server. The secure_link module allows the generation of a hashed URL that contains an expiration timestamp and an MD5 checksum of the path and a secret salt. The FastAPI backend generates this signed URL when the client requests playback. The URL looks like: /hls/track_123.m3u8?md5=aGVsbG8gd29ybGQ&expires=2147483647
When Nginx receives the request, it re-computes the hash using the URL parameters and its stored secret. If the hash matches and the timestamp is valid, it serves the file. If the link has been shared on a forum or the time has elapsed, Nginx returns a 403 Forbidden.

3.3.2 Propagation of Tokens to Segments
A common vulnerability in HLS implementations is protecting the .m3u8 manifest but leaving the .ts segments open. Sophisticated rippers can request the manifest once and then download segments directly. To counter this, the token must propagate to the segments. This can be achieved dynamically: when Nginx serves the .m3u8 file, it can use the sub_filter module to append the user's active session token to every .ts URL listed inside the manifest. Alternatively, utilizing Signed Cookies is a cleaner approach for HLS. By setting a secure, HTTP-only cookie containing the signature, the browser automatically sends the token with every request for the manifest and the subsequent segments, without needing to rewrite the manifest content.
